# Design → Execute → Audit 工作流

把工作拆成设计 → 执行 → 审计三个环节串成闭环，而不是让一个模型从头到尾自己既设计又执行又检查自己。模型分配的逻辑：设计和审计是判断力密集、低体量的环节，用**强模型**；执行是相对机械、高体量的环节，用**快模型**够了；把强模型绑定在体量小的高价值环节上，是质量和成本的双赢分配。Cursor 侧设计和审计故意用**不同模型族**（Kimi / Opus 5），避免同族盲区；Claude 侧仍共用 Opus。

骨架是设计 → 执行 → 审计三步，另有两个**按任务类型决定开不开**的环节：根因未定的 bug 类任务先过 **Step 0 根因锁定**，架构级方案在进执行前过一道 **Step 1.5 方案红队**。两个都不是默认步骤，判断标准见各自小节开头。

这个流程只负责**怎么分配模型、怎么串闭环**。改动落在哪棵工作树、打回 prompt 怎么写、审计问题定几级，全部沿用 `engineering-discipline`，本文只在需要的地方指过去，不重复抄一遍。

下文统一用 `设计模型` / `执行模型` / `审计模型` 这三个角色名，具体落到哪个模型见「模型分配」一节——**不要照抄正文里任何模型名，先查表确认当前 harness 用什么**。

**各环节是否都要开独立 subagent，必要性强度不一样——不要一视同仁**：

| 环节 | 是否必须独立 | 真正的理由 |
|---|---|---|
| Step 0 根因锁定 | **必须**（仅 bug 类任务开） | 诊断会产生大量 tool call 噪音（翻日志、跑复现、二分历史），塞进主会话会把后面几步的上下文预算烧光；且诊断本身需要持续判断，本来就该用强模型那一档 |
| Step 1 设计 | **有条件** | 主会话模型弱于设计模型，或定方案需要大量探索性读取时才开；否则主会话直接做，省掉一次有损转述 |
| Step 1.5 方案红队 | **必须**（仅架构级任务开） | 全部价值就在于不带主会话的先验；自己复查自己的方案不叫红队 |
| Step 2 执行 | **默认必须**（`直接落地` 档除外） | 执行产生大量 tool call 噪音（读文件、跑测试、看输出），塞进主会话会严重污染上下文；且模型分层本身就是这个流程的核心价值。但改动小到噪音可以忽略、方案本身又已经是精确内容时，起子代理就只剩纯开销——见 Step 1 的 `直接落地` 档 |
| Step 3 审计 | **必须** | 认知独立性，与模型强弱无关——即使主会话已经是设计模型也不能自己审。理由见 Step 3 |

## 模型分配（按 harness 分支）

先确认当前跑在哪个 harness 里，再按对应列取模型。**跨列照抄是最常见的错误**——Cursor 不接受 `opus`/`sonnet` 这类 Claude 代号，应传当前 Task 白名单里的 slug（如 `kimi-k3-max` / `claude-opus-5-thinking-max`）。传了非法 slug 时不要假装成功——按 schema 跳过并告知用户可用列表。

| 角色 | Claude Code / claude CLI | Cursor（Task `model` slug） |
|---|---|---|
| 设计模型 | Opus | `kimi-k3-max` |
| 执行模型（机械执行） | Sonnet；本机开了 GLM 派发时可换成 GLM（见 `glm-dispatch`） | `gpt-5.6-luna-max` |
| 执行模型（需要持续判断） | Opus | `kimi-k3-max` |
| 审计模型 | Opus | `claude-opus-5-thinking-max` |

> Cursor 的 slug 以**当前会话 Task 工具白名单**为准；上表是本约定的默认映射。若当前会话白名单不含目标 slug（账号/套餐/Multitask 限制），回退到提示用户切主会话模型或换可用 slug。

其它 harness（Codex 等）没有约定映射时，按"设计/审计用当前可用的最强模型、执行用次一档"的原则自己套，并在汇报时说明实际用了什么。设计与审计若能用不同模型族，优先拆开。

### 两个 harness 的机制差异（决定流程怎么走）

**两边都可全自动**。Claude Code/CLI 用 Agent 工具、Cursor 用 Task 工具，orchestrator 都能直接起不同模型的子代理并传 `model`，三步可在同一次对话里连续跑完，**不要求用户改 UI 模型选择器**。两边真正的差异是 slug 命名空间和工具名，不是「能否传 model」：

- Claude Code / CLI：Agent 工具 + `opus` / `sonnet` 等别名
- Cursor：Task 工具 + 当前会话白名单 slug（本约定：设计 / 需持续判断 → `kimi-k3-max`；审计 → `claude-opus-5-thinking-max`；机械执行 → `gpt-5.6-luna-max`）

补充说明：

- `.cursor/agents/*.md` 的 frontmatter `model`（官方 docs：`inherit` 或具体 model ID）与 Task 运行时 `model` 是两套入口；本流程优先用 Task `model`，不必为每步新建 agents 文件。
- **禁止**在 Cursor 照抄 `model: "opus"` / `"sonnet"`——Cursor 不接受这些 Claude 代号。审计用白名单 slug `claude-opus-5-thinking-max`，不要写成 `opus`。
- 仅当当前会话 Task 白名单不含目标 slug、或 plan/admin 限制导致实际模型不符时，才回退到提示用户切主会话模型 / 换可用 slug。
- 执行段和审计段共用同一个会话上下文时，审计的"认知独立性"会打折——这是两边的共性损耗，不只 Cursor。如果任务重要，让审计段开一个独立子代理（Task/Agent 自带干净 context），只带上任务描述 + 方案 + 改动范围，让它自己去读代码。

> 依据：https://cursor.com/docs/subagents（Configuration fields / Model configuration）+ 当前会话 Task 工具 schema 的 model 白名单。内置 `create-subagent` skill 可能仍只教 name/description——以官方 docs + 运行时 schema 为准，不要用它否定 `model`。

## 何时用 / 何时跳过

**用**：架构性改动、跨文件重构、有非平凡边界情况的 bug 修复、任何"改错了代价很高"的任务、用户明确要求更高把握的场景。

**跳过**：真正的单行/机械性修复（改个常量、加个 import）、纯粹的探索性问题（不涉及写代码）、用户已经明确说"别搞这么重，先给个方案/直接改就行"。跳过时不要提这个流程存在的仪式感，直接干活。

**成本提示**：完整跑一轮至少是 1 次执行 + 1 次强模型审计，设计如果也开子代理就再加 1 次强模型。**架构级的复杂 bug 修复是最贵的形态**——Step 0 根因锁定和 Step 1.5 方案红队各再加一次强模型，一轮可能到 5 次调用；如果审计不过重跑，成本还会翻倍。这是主动的质量/成本权衡，不是默认对每个任务都套用的东西——判断不准就问用户要不要走这套流程，别自作主张升级。反过来，改动量小的任务用 `直接落地` 档能省掉执行那一次调用，判据见 Step 1。

## 触发方式：显式 vs 隐式

- **显式触发**（用户输入 `/design-execute-audit <任务>`，或明确说出触发短语）→ 直接开始，不用再确认一遍。
- **隐式触发**（我自己判断当前任务匹配这个技能的 description，用户没有显式提这个流程）→ **先用一句话确认再开始**，确认语里带上当前 harness 实际会用的模型名，比如"这个任务看起来适合走 design-execute-audit（Opus 设计 + 审计、Sonnet 执行），要跑吗？"；在 Cursor 里则是"…（Kimi 设计、Opus 5 审计、GPT 机械执行，同会话 Task 自动起子代理），要跑吗？"。用户确认后视为已授权传约定 slug，直接起第一个环节（根因未定的 bug 类任务是 Step 0，其余是 Step 1）。**要跑满 Step 0 和 Step 1.5 的任务，确认语里得把这一轮的大致调用次数说出来**——架构级 bug 修复一轮可能到 5 次强模型调用，别让用户按三次的价钱点头。不要因为判断匹配就直接开始烧多次强模型调用——这套流程成本不低，用户应该在花钱之前知情，而不是事后看汇报才知道跑了什么。旧触发语「kimi设计gpt执行」「grok设计kimi审计」仍识别为同一流程，但 Cursor 侧按上表执行（设计/需持续判断用 Kimi，审计用 Opus 5）。

## 改动隔离与任务资源

这个流程天生是**一条逻辑任务链**：设计 → 执行 → 审计 → 打回重执行 → 重审计，中间换了好几个模型和好几个子代理，但从头到尾是同一个任务。`engineering-discipline` 的 `Task Resource Reuse and Continuation` 讲的正是这种链条，直接照它办：

- **进 Step 2 之前，主会话先把工作树和分支定下来**：为这条任务链建一个独立 worktree + 专用分支，不在仓库主 checkout、也不在默认/保护分支上写。建完记下三个坐标——**绝对路径、分支名、baseline HEAD**。
- **整条链复用同一棵工作树和同一个分支**。执行、打回重执行、审计读 diff、重审计，全在那一棵树上；不要每个 subagent 各开一棵，也不要把改动从一棵树拷进另一棵。只有在出现真正并行的另一条改动流、或这棵树已损坏/被别的写者占用时才换，换了要说明原因和新路径。
- **主会话负责把坐标带进每一段 prompt**。子代理不共享你的上下文，坐标没写进 prompt 就等于没有；这也是 `engineering-discipline` 里认可的显式交接形式，接手方不需要再找用户确认一次。
- **Step 1 设计是只读的，可以在主 checkout 里做**。工作树在第一次要写文件之前建起来就行。
- **过程文档不进仓库**：Step 1 的方案原文、Step 3 的审计结论、打回 prompt，都属于 `Process Documents Stay Out of the Repository` 说的过程材料，写到项目对应的 out-of-tree handoff 目录，不要提交进这个分支。
- **建了 worktree 不等于获得推送授权**。push、开 PR、删旧资源都要用户明确要求，跑完闭环默认停在本地分支上等用户处置。

## 三步循环

骨架是下面的 Step 1 / 2 / 3。**Step 0 和 Step 1.5 是按任务类型决定开不开的可选环节**，不要因为它们写在这里就默认跑——判断标准写在各自小节的第一段。

### Step 0 — 根因锁定（设计模型，必须独立子代理；仅 bug 类任务）

**只有根因尚未确定的 bug 类任务需要这一步**。从零实现的任务、或根因已由用户指明 / 前面的调查坐实的任务，跳过，直接进 Step 1。

存在的理由很窄但很硬：架构级的修复方案一旦建立在错的根因上，后面每一步都在错的问题上加码——执行子代理照方案改完，审计对着方案核对**也会 PASS**，因为审计核的是"实现有没有还原方案"，不是"方案针对的问题存不存在"。这种失败要到用户实测才暴露，那时整轮成本已经花完。Step 2 的中途升级机制救不了它：那个机制触发得太晚（方案已出、子代理已起），而且它默认根因是执行过程中顺手能定的，架构级 bug 的根因通常不是。

- **必须开独立子代理**，用设计模型那一档（Claude Code: `model: "opus"` / Cursor: `kimi-k3-max`）。理由见开头的独立性表格。
- **只产出根因，不产出修复方案**。要求输出：根因陈述、支撑证据（`file:line`、日志片段、复现步骤、相关提交哈希）、以及这个根因能解释多少已观察到的现象——**解释不了的现象必须单独列出来**，那往往意味着还有第二个原因，而只修掉一个的方案会通过审计然后在生产上继续出问题。
- **禁止拿猜测冒充结论**。"最可能的原因是"、"通常这类问题是因为"这种没有证据支撑的表述不算锁定。证据不足时走下面的第二条出口——这是这道门存在的全部意义，绕过它这一步就白开了。
- 诊断是只读的，可以在主 checkout 上做；工作树仍然留到 Step 2 之前再建。

产出必须落在两条出口之一：

- **`根因已锁定`** + 证据 → 进 Step 1，把根因和证据**原文**带进设计输入。
- **`根因未锁定`** + 已排除的方向及排除依据 + 下一步该看什么 → 不许硬凑一个。这时有两条路：证据明显在收敛，就再跑一轮 Step 0，把上一轮的证据原样带过去（不要让它从头重查一遍）；已经收敛不动了，就把"排查方向"当作方案进 Step 1，让方案显式标注 `执行层级：需要持续判断`，交给强模型那一档边执行边定位——这是现有机制，不是新东西。
- **诊断轮次上限默认 2 轮**。两轮还没锁定就停下来问用户，把两轮的证据和已排除方向汇总汇报，不要自己一直查下去。

### Step 1 — 设计（设计模型）

**走过 Step 0 的话，先把根因和证据原文接进来**——不管 Step 1 是主会话自己做还是开子代理，设计的输入都必须包含 Step 0 的完整结论和证据链。转述会把证据压成一句话，而证据链正是 Step 3 判断"方案是不是在针对真问题"的唯一依据。

**先判断这一步要不要开子代理**。满足任一条件 → 开（Claude Code 用 Agent 工具起 `model: "opus"`；Cursor 用 Task 工具起 `subagent_type: "generalPurpose"` + `model: "kimi-k3-max"`）；两个都不满足 → 主会话自己出方案（架构级任务仍然要过 Step 1.5 红队才能进 Step 2）。

- **主会话模型弱于设计模型**（比如 Claude Code 里主会话是 Sonnet；或 Cursor 主会话不是 Kimi K3 档）→ 开。这是唯一能让设计环节用上强模型的路径，也是这个流程最初的设计意图。
- **定方案需要大量探索性读取**（要翻十几个文件才能决定怎么改）→ 开。子代理只回传结论，主会话省下上下文预算。

主会话**已经就是设计模型**且相关文件都读过时，**不要**为了流程完整性而开这个子代理：拿到的是同一个模型 + 更少的上下文，纯负收益。设计环节的上下文损失是整条链里最贵的——主会话此时手里有跟用户来回澄清出来的真实意图、已读过的文件、项目规则、之前踩过的坑，这些全靠转述进 prompt 必然有损，尤其是"用户其实更在意 A 不是 B"这类软性约束最容易丢。

设计阶段只产出**方案**，不写代码——因为不写，这一步可以直接在主 checkout 上读代码，工作树留到 Step 2 之前再建：

- Prompt 必须自包含：任务目标、已知的相关文件路径/代码摘录（你在主对话里已经读过的直接喂进去，不要让它重新盲找一遍你已经知道的东西）、任何已知约束（项目规范、之前踩过的坑、用户明确提过的偏好）。
- 明确要求输出：具体要改哪些文件、每个文件改什么、为什么这么改、需要覆盖哪些边界情况、怎么验证（对应项目的测试/构建命令）。
- **粒度按「设计判断 / 实现判断」的分界划，不是按详细程度划**。方案负责**设计判断**——改哪、为什么、边界是什么、怎么验证；执行者负责**实现判断**——具体怎么写、变量怎么命名、代码怎么组织。**不要在方案里替执行者写出最终代码**：写完了执行环节就没活干，一次强模型把方案写成成品、再付一次子代理的启动 + 读文件 + 写文件 + 汇报，比压根不分层还贵。
  - **窄例外**：描述比代码本身还长的时候，直接给代码——短而逻辑微妙的片段、必须一字不差的常量 / 正则 / 配置字段 / 协议字面量。给的时候标注「精确内容，照抄」，让执行者知道这段不许自由发挥。
  - **反向也要防**：为了回避写代码而用三百字自然语言绕着描述一个五行就说得清的改动，是另一种浪费，执行者还得反推你到底在说什么。判据始终是「执行者还需不需要做设计判断」，不是字数多少。
- **额外要求输出一个执行层级标注**，三选一：`执行层级：需要持续判断` / `执行层级：机械执行` / `执行层级：直接落地`。这个标注直接决定 Step 2 怎么走，不是可选项。
  - `需要持续判断`——方案里「具体怎么改」天然依赖执行过程中才能确定的信息（典型例子：诊断类问题的根因要跑起来看证据才能定，方案只能给排查方向，给不出具体改法）。
  - `机械执行`——方案给全了设计判断，但执行者仍有实打实的实现判断要做，且改动量大到值得把 tool call 噪音隔离出去。**这是默认档**。
  - `直接落地`——改动集中在一两个文件、总量很小，而且方案因为上面那条窄例外已经把精确内容写出来了。这时**不起执行子代理**，由设计环节自己把改动落进工作树，然后照常进 Step 3 审计（走法见 Step 2）。
  - **`直接落地` 是窄档，不是逃生口**。它卡的是**改动量**，不是「方案写得够不够具体」。分层有两个价值——模型成本分层、上下文隔离——方案写成成品只消解了前一个，后一个还在：文件一多，哪怕每处内容都精确，也要起执行子代理，否则大量文件 IO 会把设计/主会话的上下文冲掉。拿不准就标 `机械执行`。
- 前台运行（`run_in_background: false`）——执行阶段需要这份方案才能开始，没有可以并行的事。两边一致；若用户处于 Multitask Mode，按 schema 设 `run_in_background: true`，用完成通知汇合，仍保持步骤依赖序，不要并行打乱闭环。

**主会话自己出方案时，上面的输出要求同样适用**：粒度按同一条「设计判断 / 实现判断」分界划，执行层级标注一样要给。省掉的只是 subagent 这一层，不是设计的严谨度——方案照样要写成完整文本（`直接落地` 档也一样，它是 Step 3 审计的输入），不能停在自己心里有数。

### Step 1.5 — 方案红队（设计模型，必须独立子代理；仅架构级任务）

**架构级任务才开**：方案会引入或改动一层抽象、跨模块边界、影响后续怎么扩展。方案只是"在已有结构里加个分支"这种量级就跳过。

它针对的失败模式和 Step 3 不是一个：审计问"实现对不对"，红队问"这个方案是不是过重"。架构方案最常见的问题不是错——错会被审计和测试抓到——而是**过度**：多了一层用不上的抽象，能跑，只是把成本推到以后。现有环节没有一个会去质疑这件事，因为方案在它自己的框架内部总是自洽的。

- **必须开独立子代理**。它的全部价值就是不带主会话的先验；主会话复查自己的方案不叫红队。
- **只挑毛病，不出替代方案**。要求它按三个角度逐条挑战：
  1. 方案里哪一层 / 哪个抽象可以直接砍掉，任务目标仍然达成？
  2. 有没有明显更简单的路径，被这个方案的框架挡在视野之外了？
  3. 哪些复杂度是在应对"可能以后需要"，而不是当前任务真实要求的？
- **prompt 里必须附「已排除的选项及其原因」**——主会话跟用户澄清过程中否掉的方向、项目历史上踩过的坑。不给这段，红队会大量产出"你没考虑 X"，而 X 早就讨论过并否了，全是噪音。这是这一步最主要的失败模式，也是它唯一真正需要防的东西。
- **红队不阻塞，不给 PASS / FAIL**。它输出逐条挑战 + 每条自评"建议采纳 / 可忽略"，采不采纳由主会话定。这点必须跟 Step 3 区分清楚：红队是设计环节的延伸，审计才是关口。
- 采纳了就改方案再进 Step 2；**没采纳的要在方案里补一句为什么**，这样 Step 3 审计能看出这个点已经权衡过，不会当成新发现再提一遍。

### Step 2 — 执行（执行模型，档位取决于 Step 1 的标注）

方案定稿后开始实现（架构级任务是过完 Step 1.5、该改的都改完之后），**按 Step 1 的执行层级标注走**：`机械执行` → 起执行子代理，用执行模型（Claude Code: Sonnet / Cursor: GPT）；`需要持续判断` → 起执行子代理，用设计模型那一档（Claude Code: Opus / Cursor: Kimi）；`直接落地` → **不起执行子代理**，由设计环节（主会话，或 Step 1 那个设计子代理）自己把改动落进工作树、跑完项目的验证流程，然后照常进 Step 3。用户在触发这个流程时已经明确要求全程用强模型的，直接按用户要求来，不用等 Step 1 的判断。

`直接落地` 省掉的只是执行这一次子代理调用，**不省 Step 3**——改动是设计环节自己落的，审计的独立性比平时更要紧。落地的人照样要交出那份自我报告（改了哪些文件、关键 diff 摘要、验证命令的实际输出和退出码、有没有偏离方案），它是审计的输入，不能因为「反正是自己改的」就跳过。

怎么起：Claude Code 用 Agent 工具起 subagent、`model` 参数按上面选；Cursor 用 Task 工具起 `subagent_type: "generalPurpose"` + 对应 slug（机械执行 `gpt-5.6-luna-max` / 需持续判断 `kimi-k3-max`），执行在独立子代理里进行。

**Claude Code 下机械执行档还有一个可选执行器**：派给跑在智谱 GLM 上的 claude CLI，换的是账单来源（不吃 Claude 额度），能力档位仍是「机械执行」这一格。**先按 `glm-dispatch` 技能的 Step 0 实地探测本机开关**——`READY` 才派，`FALLBACK` 就照常用 Sonnet，并且不要向用户提起 GLM 这回事（这台设备没开就是答案）。派发方式、方案文件要求、拿回结果后的必查项都在那个技能里，不在这里重复。

不管哪个 harness，交给执行者的输入和要求都一样：

- **Prompt 开头先给执行坐标**：worktree 绝对路径、分支名、baseline HEAD、期望的 `git status` 状态，并写明「在这棵树上继续，不要另建 worktree」。要求它在第一条实质命令之前先核对路径/分支/HEAD/`git status --short`，对不上就停下报告，不要接着写。
- Prompt 的写法按 `engineering-discipline` 的 `Audit-to-Implementation Prompt Design` 来：任务局部的增量信息写满（坐标、证据、必须的行为、反例、验证命令、交付物），已经由项目规则和 skill 保证的通用条款不要再抄一遍。
- Prompt 里把 Step 1 的方案**原文**带上（不要转述，转述容易丢细节），加上原始任务描述，明确要求"严格按此方案实现；如果方案有明显不可行的地方，实现你认为对的版本但显式报告偏离了方案的哪一点、为什么"。
- 要求它真正落地改动（不是描述打算怎么改），并跑项目既有的验证流程（格式化/lint/测试——具体命令让它自己在项目规则里找，不要在这里替它猜）。
- 要求它在最终回复里给出：改了哪些文件、关键 diff 摘要、验证命令的实际输出/退出码、有没有偏离方案。
- 前台运行——审计阶段需要这份结果。

**中途升级（哪怕起点选了快模型）**：必须明确告诉执行者——如果实际情况比方案假设的更开放（比如"这个 bug 不是方案说的那个原因，真正根因还没定位清楚，需要进一步排查"），**不允许硬凑一个看起来合理但没验证过的修复**。要求它停下来，如实报告已经排查到的证据和进展，不强行给出修复。收到这类报告后，换成强模型那一档（Claude Code: `model: "opus"` / Cursor: Task `model: "kimi-k3-max"`）重新跑一次 Step 2，把上一轮已经收集的排查证据原样带过去（不要浪费它做过的调查工作），接着做诊断和修复。这次不用回 Step 1 重新出方案——问题不在方案本身，在于这个任务的执行环节天然需要持续判断，起点错误分配了模型层级。

**`直接落地` 档撞上同样情形**（动手才发现方案的假设不成立）也一样停手，但升级方向不同：这一档本来就是强模型在做，换模型无解——该回 Step 1 重出方案；如果连根因都动摇了，回 Step 0。

### Step 3 — 审计（审计模型）

**这一步永远独立进行，没有例外**——包括主会话本身就是设计模型的情况，也包括 `直接落地` 档（改动就是设计环节自己落的，那正是自审自纠的靶心）。理由不是"这个模型更强"，而是独立性：

- 主会话作为 orchestrator，已经看过方案、看过执行者的自我报告，带着"这个方案是对的"的先验去读 diff，是确认偏误最容易发生的位置。审计的全部价值就在于独立核实，被锚定过的审计者等于没审。
- 如果方案还是主会话自己出的（Step 1 走了"主会话直接做"分支），那主会话审计就是自审自纠，正是这个流程开头要避免的东西。
- 机制上还有一层：方案作者自己传达"审计发现方案有缺陷"这个结论，可信度天然打折。
- Cursor 侧审计模型（Opus 5）与设计模型（Kimi）刻意不同族：即使主会话已经是 Kimi，审计仍必须起独立的 Opus 5 子代理，不能用 Kimi 自审。

执行结果出来后做审计：Claude Code 用 Agent 工具起 `model: "opus"` 的 subagent；Cursor 用 Task 工具起 `subagent_type: "generalPurpose"` + `model: "claude-opus-5-thinking-max"` 的子代理（Task/子代理自带干净 context，已提供独立性；重要任务可进一步只带任务描述 + 方案 + 改动范围，让它自己去读代码）。要求一致：

- **Prompt 里必须给出审计对象的物理位置**：同一棵 worktree 的绝对路径、分支、baseline HEAD 和当前 HEAD，以及具体的读取命令（如 `git -C <路径> diff <baseline>..HEAD`）。一台开发机上常常并存多棵工作树，只说"去读 diff"没有指明位置，审计模型很可能读到别的分支，或者读到主 checkout 上跟本任务无关的改动，然后给出一份看起来煞有介事的错误结论。
- **确认执行者已经停手再审**。执行 subagent 还在写的时候审计等于审一个移动靶；审计过程中如果 HEAD、`git status`、文件 mtime 意外变了，按 `engineering-discipline` 的规定作废本轮结论并报告写者冲突，不要硬给结论。
- Prompt 里带上：原始任务、Step 1 的方案、Step 2 报告的改动摘要和验证结果。**不要只给摘要，让它自己去读实际的 diff / 改动后的文件**——复述执行者的自我报告不算审计。
- 明确要求：核对实现是否真的满足了任务目标和方案里列的边界情况；找执行者自己想不到的问题（逻辑漏洞、遗漏的边界、验证是否真的跑了而不是声称跑了）；同时判断如果有问题，责任在**执行环节做错了**、**方案本身就有缺陷**、还是**方案针对的根因判断就是错的**（第三档只在走过 Step 0 的任务上适用）——这个归因直接决定循环怎么走（见下），归错了就会在错的环节上反复重试。
- **任务走过 Step 0 的话，把根因和证据一并交给审计核验**，并明确要求它回答：改完之后，Step 0 列出的现象是不是都被解释并消除了？当时那些「解释不了的现象」还在不在？这是交付前唯一能发现根因判错的检查点——只核对「实现有没有还原方案」是发现不了的。
- **严重程度按 `engineering-discipline` 的 `Audit Calibration` 定档**，别让审计模型自己发明标准：只有由本次改动引入、或直接挡住任务目标的问题才算阻塞项；顺手发现的历史欠债、缺测试、纯观感问题记下来但不阻塞，也不要借审计把任务范围撑大。
- 要求输出清晰的结论：`AUDIT PASS`（可以附带非阻塞性建议），或者 `AUDIT FAIL` + 逐条列出阻塞性问题，并标注每条问题属于哪一档：`执行偏离方案` / `方案本身有缺陷` / `根因判断错误`。

## 循环规则

- **审计通过** → 结束，向用户汇报做了什么、审计确认了什么。
- **审计不过，问题出在执行层面**（方案是对的，执行没做到位）→ 回到 Step 2，把 Step 3 的具体问题原文带给新一轮执行 subagent，让它针对性修复，然后重新走 Step 3 审计。`直接落地` 档同理，只是动手改的仍是设计环节自己——但重新审计**必须再起一个独立子代理**，不能因为这轮改动量小就自己看一眼了事。
- **每一次打回都在同一棵 worktree、同一个分支上增量修，重审计也审这棵树**。新一轮执行 subagent 的 prompt 照样要带全坐标（路径/分支/当前 HEAD/期望 status），并写明这是承接上一轮的交接；打回 prompt 本身按 `Audit-to-Implementation Prompt Design` 写，只带这一轮真正要改的东西，不要把前几轮的完整审计报告整篇塞回去。
- **审计不过，问题出在方案层面**（执行忠实还原了方案，但方案本身有缺陷）→ 回到 Step 1 重新出方案，把审计发现的方案缺陷原文带上，然后走 Step 2 执行 + Step 3 审计。不要在一个有缺陷的方案上反复打补丁式执行。**重做时 Step 1 一律用独立的设计模型跑**——哪怕第一轮是主会话自己出的方案：审计已经证明主会话在这个任务上的设计判断不够，让它再自己想一遍大概率是同一个盲区。
- **审计不过，问题出在根因层面**（方案忠实针对了 Step 0 给出的根因，但那个根因本身错了或不完整）→ 回到 Step 0 重新诊断，把审计发现的反证原文带上：哪些现象这个根因解释不了、改完之后哪些症状还在。这是最贵的一种打回，也正是 Step 0 那道门要防的事——**如果这种打回反复发生，说明 Step 0 被跳过了，或者它输出了没有证据支撑的猜测而被当成了锁定**，先去修那个，不要在这一层反复重诊断。
- **方案重做时红队跟着重跑**（限开了 Step 1.5 的任务）：新方案没经过红队，跟第一版不是同一个成熟度。根因重做后重新出的方案同理。
- **重试时重新判断模型层级，不要在同一个误判上原地重试**：不管打回 Step 1 还是 Step 2，如果审计发现症结在于"这类任务本来就需要持续判断，之前却当成机械执行分配了快模型"，重试时对应步骤直接升级到强模型那一档；不要指望换一版 prompt 就能让快模型在同一类任务上蒙对。同理，如果发现 `直接落地` 标错了——改动量实际比预想的大，设计环节自己落地反而把上下文冲掉了，或者根本落不完——重试时改标 `机械执行` 起执行子代理，别硬着头皮在原档里接着干。
- **迭代上限**：默认最多 3 轮"执行→审计"（不含方案重做、不含根因重做、不含中途升级换模型那一次；Step 0 自身的诊断轮次另有 2 轮上限）。达到上限仍未通过，停下来，把最后一次审计的阻塞项如实汇报给用户，问接下来怎么处理——不要为了"完成"而悄悄放宽标准或自己宣布通过。用户可以在触发时加参数覆盖这个上限（比如"最多跑 5 轮"）。

## 完成后怎么汇报

不管走了几轮，最后用简短的中文总结：**改动落在哪棵 worktree 的哪个分支**、改了什么、审计确认了哪些点、（走过 Step 0 的话）根因是什么以及坐实它的关键证据、（如果有）重新设计过几次分别是为什么、最终验证结果（测试/构建的真实输出，不是"应该没问题"）。工作树和分支要报出来——用户接下来要自己决定怎么测、怎么合入，找不到改动在哪就没法接手。不要展示中间每一轮 subagent 的完整输出——那是过程，不是给用户看的交付物。
