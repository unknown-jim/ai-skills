# Design → Execute → Audit 工作流

把工作拆成设计 → 执行 → 审计三个环节串成闭环，而不是让一个模型从头到尾自己既设计又执行又检查自己。模型分配的逻辑：设计和审计是判断力密集、低体量的环节，用**强模型**；执行是相对机械、高体量的环节，用**快模型**够了；把强模型绑定在体量小的高价值环节上，是质量和成本的双赢分配。

下文统一用 `设计模型` / `执行模型` 这两个角色名，具体落到哪个模型见「模型分配」一节——**不要照抄正文里任何模型名，先查表确认当前 harness 用什么**。

**三个环节是否都要开独立 subagent，必要性强度不一样——不要一视同仁**：

| 环节 | 是否必须独立 | 真正的理由 |
|---|---|---|
| 设计 | **有条件** | 主会话模型弱于设计模型，或定方案需要大量探索性读取时才开；否则主会话直接做，省掉一次有损转述 |
| 执行 | **必须** | 执行产生大量 tool call 噪音（读文件、跑测试、看输出），塞进主会话会严重污染上下文；且模型分层本身就是这个流程的核心价值 |
| 审计 | **必须** | 认知独立性，与模型强弱无关——即使主会话已经是设计模型也不能自己审。理由见 Step 3 |

## 模型分配（按 harness 分支）

先确认当前跑在哪个 harness 里，再按对应列取模型。**跨列照抄是最常见的错误**——Cursor 不接受 `opus`/`sonnet` 这类 Claude 代号，应传当前 Task 白名单里的 slug（如 `kimi-k3-max`）。传了非法 slug 时不要假装成功——按 schema 跳过并告知用户可用列表。

| 角色 | Claude Code / claude CLI | Cursor（Task `model` slug） |
|---|---|---|
| 设计模型 | Opus | `kimi-k3-max` |
| 执行模型（机械执行） | Sonnet | `gpt-5.6-luna-max` |
| 执行模型（需要持续判断） | Opus | `kimi-k3-max` |
| 审计模型 | Opus | `kimi-k3-max` |

> Cursor 的 slug 以**当前会话 Task 工具白名单**为准；上表是本约定的默认映射。若当前会话白名单不含目标 slug（账号/套餐/Multitask 限制），回退到提示用户切主会话模型或换可用 slug。

其它 harness（Codex 等）没有约定映射时，按"设计/审计用当前可用的最强模型、执行用次一档"的原则自己套，并在汇报时说明实际用了什么。

### 两个 harness 的机制差异（决定流程怎么走）

**两边都可全自动**。Claude Code/CLI 用 Agent 工具、Cursor 用 Task 工具，orchestrator 都能直接起不同模型的子代理并传 `model`，三步可在同一次对话里连续跑完，**不要求用户改 UI 模型选择器**。两边真正的差异是 slug 命名空间和工具名，不是「能否传 model」：

- Claude Code / CLI：Agent 工具 + `opus` / `sonnet` 等别名
- Cursor：Task 工具 + 当前会话白名单 slug（本约定：设计/审计/需持续判断 → `kimi-k3-max`；机械执行 → `gpt-5.6-luna-max`）

补充说明：

- `.cursor/agents/*.md` 的 frontmatter `model`（官方 docs：`inherit` 或具体 model ID）与 Task 运行时 `model` 是两套入口；本流程优先用 Task `model`，不必为每步新建 agents 文件。
- **禁止**在 Cursor 照抄 `model: "opus"` / `"sonnet"`——Cursor 不接受这些 Claude 代号。
- 仅当当前会话 Task 白名单不含目标 slug、或 plan/admin 限制导致实际模型不符时，才回退到提示用户切主会话模型 / 换可用 slug。
- 执行段和审计段共用同一个会话上下文时，审计的"认知独立性"会打折——这是两边的共性损耗，不只 Cursor。如果任务重要，让审计段开一个独立子代理（Task/Agent 自带干净 context），只带上任务描述 + 方案 + 改动范围，让它自己去读代码。

> 依据：https://cursor.com/docs/subagents（Configuration fields / Model configuration）+ 当前会话 Task 工具 schema 的 model 白名单。内置 `create-subagent` skill 可能仍只教 name/description——以官方 docs + 运行时 schema 为准，不要用它否定 `model`。

## 何时用 / 何时跳过

**用**：架构性改动、跨文件重构、有非平凡边界情况的 bug 修复、任何"改错了代价很高"的任务、用户明确要求更高把握的场景。

**跳过**：真正的单行/机械性修复（改个常量、加个 import）、纯粹的探索性问题（不涉及写代码）、用户已经明确说"别搞这么重，先给个方案/直接改就行"。跳过时不要提这个流程存在的仪式感，直接干活。

**成本提示**：完整跑一轮至少是 1 次执行 + 1 次强模型审计，设计如果也开子代理就再加 1 次强模型；如果审计不过重跑，成本还会翻倍。这是主动的质量/成本权衡，不是默认对每个任务都套用的东西——判断不准就问用户要不要走这套流程，别自作主张升级。

## 触发方式：显式 vs 隐式

- **显式触发**（用户输入 `/design-execute-audit <任务>`，或明确说出触发短语）→ 直接开始，不用再确认一遍。
- **隐式触发**（我自己判断当前任务匹配这个技能的 description，用户没有显式提这个流程）→ **先用一句话确认再开始**，确认语里带上当前 harness 实际会用的模型名，比如"这个任务看起来适合走 design-execute-audit（Opus 设计 + 审计、Sonnet 执行），要跑吗？"；在 Cursor 里则是"…（Kimi 设计 + 审计、GPT 执行，同会话 Task 自动起子代理），要跑吗？"。用户确认后视为已授权传约定 slug，直接起 Step 1。不要因为判断匹配就直接开始烧多次强模型调用——这套流程成本不低，用户应该在花钱之前知情，而不是事后看汇报才知道跑了什么。

## 三步循环

### Step 1 — 设计（设计模型）

**先判断这一步要不要开子代理**。满足任一条件 → 开（Claude Code 用 Agent 工具起 `model: "opus"`；Cursor 用 Task 工具起 `subagent_type: "generalPurpose"` + `model: "kimi-k3-max"`）；两个都不满足 → 主会话自己出方案，直接进 Step 2。

- **主会话模型弱于设计模型**（比如 Claude Code 里主会话是 Sonnet）→ 开。这是唯一能让设计环节用上强模型的路径，也是这个流程最初的设计意图。
- **定方案需要大量探索性读取**（要翻十几个文件才能决定怎么改）→ 开。子代理只回传结论，主会话省下上下文预算。

主会话**已经就是设计模型**且相关文件都读过时，**不要**为了流程完整性而开这个子代理：拿到的是同一个模型 + 更少的上下文，纯负收益。设计环节的上下文损失是三步里最贵的——主会话此时手里有跟用户来回澄清出来的真实意图、已读过的文件、项目规则、之前踩过的坑，这些全靠转述进 prompt 必然有损，尤其是"用户其实更在意 A 不是 B"这类软性约束最容易丢。

设计阶段只产出**方案**，不写代码：

- Prompt 必须自包含：任务目标、已知的相关文件路径/代码摘录（你在主对话里已经读过的直接喂进去，不要让它重新盲找一遍你已经知道的东西）、任何已知约束（项目规范、之前踩过的坑、用户明确提过的偏好）。
- 明确要求输出：具体要改哪些文件、每个文件改什么、为什么这么改、需要覆盖哪些边界情况、怎么验证（对应项目的测试/构建命令）。方案要具体到"下一个执行者不需要再做设计判断，只需要照着写"的粒度。
- **额外要求输出一个执行层级标注**：`执行层级：机械执行` 或 `执行层级：需要持续判断`。判断标准——如果方案里"具体怎么改"天然依赖执行过程中才能确定的信息（典型例子：诊断类问题的根因要跑起来看证据才能定，方案只能给排查方向，给不出具体改法），标"需要持续判断"；如果方案已经具体到照抄就能做对，标"机械执行"。这个标注直接决定 Step 2 用哪个模型，不是可选项。
- 前台运行（`run_in_background: false`）——执行阶段需要这份方案才能开始，没有可以并行的事。两边一致；若用户处于 Multitask Mode，按 schema 设 `run_in_background: true`，用完成通知汇合，仍保持步骤依赖序，不要并行打乱闭环。

**主会话自己出方案时，上面的输出要求同样适用**：粒度要到"执行者不需要再做设计判断"，执行层级标注一样要给。省掉的只是 subagent 这一层，不是设计的严谨度——方案照样要写成能原文交给 Step 2 的完整文本，不能停在自己心里有数。

### Step 2 — 执行（执行模型，档位取决于 Step 1 的标注）

方案出来后开始实现，**模型按 Step 1 的执行层级标注选**：`机械执行` → 执行模型（Claude Code: Sonnet / Cursor: GPT）；`需要持续判断` → 直接用设计模型那一档（Claude Code: Opus / Cursor: Kimi）。用户在触发这个流程时已经明确要求全程用强模型的，直接按用户要求来，不用等 Step 1 的判断。

怎么起：Claude Code 用 Agent 工具起 subagent、`model` 参数按上面选；Cursor 用 Task 工具起 `subagent_type: "generalPurpose"` + 对应 slug（机械执行 `gpt-5.6-luna-max` / 需持续判断 `kimi-k3-max`），执行在独立子代理里进行。

不管哪个 harness，交给执行者的输入和要求都一样：

- Prompt 里把 Step 1 的方案**原文**带上（不要转述，转述容易丢细节），加上原始任务描述，明确要求"严格按此方案实现；如果方案有明显不可行的地方，实现你认为对的版本但显式报告偏离了方案的哪一点、为什么"。
- 要求它真正落地改动（不是描述打算怎么改），并跑项目既有的验证流程（格式化/lint/测试——具体命令让它自己在项目规则里找，不要在这里替它猜）。
- 要求它在最终回复里给出：改了哪些文件、关键 diff 摘要、验证命令的实际输出/退出码、有没有偏离方案。
- 前台运行——审计阶段需要这份结果。

**中途升级（哪怕起点选了快模型）**：必须明确告诉执行者——如果实际情况比方案假设的更开放（比如"这个 bug 不是方案说的那个原因，真正根因还没定位清楚，需要进一步排查"），**不允许硬凑一个看起来合理但没验证过的修复**。要求它停下来，如实报告已经排查到的证据和进展，不强行给出修复。收到这类报告后，换成强模型那一档（Claude Code: `model: "opus"` / Cursor: Task `model: "kimi-k3-max"`）重新跑一次 Step 2，把上一轮已经收集的排查证据原样带过去（不要浪费它做过的调查工作），接着做诊断和修复。这次不用回 Step 1 重新出方案——问题不在方案本身，在于这个任务的执行环节天然需要持续判断，起点错误分配了模型层级。

### Step 3 — 审计（设计模型那一档）

**这一步永远独立进行，没有例外**——包括主会话本身就是设计模型的情况。理由不是"这个模型更强"，而是独立性：

- 主会话作为 orchestrator，已经看过方案、看过执行者的自我报告，带着"这个方案是对的"的先验去读 diff，是确认偏误最容易发生的位置。审计的全部价值就在于独立核实，被锚定过的审计者等于没审。
- 如果方案还是主会话自己出的（Step 1 走了"主会话直接做"分支），那主会话审计就是自审自纠，正是这个流程开头要避免的东西。
- 机制上还有一层：方案作者自己传达"审计发现方案有缺陷"这个结论，可信度天然打折。

执行结果出来后做审计：Claude Code 用 Agent 工具起 `model: "opus"` 的 subagent；Cursor 用 Task 工具起 `subagent_type: "generalPurpose"` + `model: "kimi-k3-max"` 的子代理（Task/子代理自带干净 context，已提供独立性；重要任务可进一步只带任务描述 + 方案 + 改动范围，让它自己去读代码）。要求一致：

- Prompt 里带上：原始任务、Step 1 的方案、Step 2 报告的改动摘要和验证结果。**不要只给摘要，让它自己去读实际的 diff / 改动后的文件**——复述执行者的自我报告不算审计。
- 明确要求：核对实现是否真的满足了任务目标和方案里列的边界情况；找执行者自己想不到的问题（逻辑漏洞、遗漏的边界、验证是否真的跑了而不是声称跑了）；同时判断如果有问题，根因是**执行环节做错了**还是**方案本身就有缺陷**——这个判断直接决定循环怎么走（见下）。
- 要求输出清晰的结论：`AUDIT PASS`（可以附带非阻塞性建议），或者 `AUDIT FAIL` + 逐条列出阻塞性问题，并标注每条问题是"执行偏离方案"还是"方案本身有缺陷"。

## 循环规则

- **审计通过** → 结束，向用户汇报做了什么、审计确认了什么。
- **审计不过，问题出在执行层面**（方案是对的，执行没做到位）→ 回到 Step 2，把 Step 3 的具体问题原文带给新一轮执行 subagent，让它针对性修复，然后重新走 Step 3 审计。
- **审计不过，问题出在方案层面**（执行忠实还原了方案，但方案本身有缺陷）→ 回到 Step 1 重新出方案，把审计发现的方案缺陷原文带上，然后走 Step 2 执行 + Step 3 审计。不要在一个有缺陷的方案上反复打补丁式执行。**重做时 Step 1 一律用独立的设计模型跑**——哪怕第一轮是主会话自己出的方案：审计已经证明主会话在这个任务上的设计判断不够，让它再自己想一遍大概率是同一个盲区。
- **重试时重新判断模型层级，不要在同一个误判上原地重试**：不管打回 Step 1 还是 Step 2，如果审计发现根因是"这类任务本来就需要持续判断，之前却当成机械执行分配了快模型"，重试时对应步骤直接升级到强模型那一档；不要指望换一版 prompt 就能让快模型在同一类任务上蒙对。
- **迭代上限**：默认最多 3 轮"执行→审计"（不含方案重做、不含中途升级换模型那一次）。达到上限仍未通过，停下来，把最后一次审计的阻塞项如实汇报给用户，问接下来怎么处理——不要为了"完成"而悄悄放宽标准或自己宣布通过。用户可以在触发时加参数覆盖这个上限（比如"最多跑 5 轮"）。

## 完成后怎么汇报

不管走了几轮，最后用简短的中文总结：改了什么、审计确认了哪些点、（如果有）重新设计过几次分别是为什么、最终验证结果（测试/构建的真实输出，不是"应该没问题"）。不要展示中间每一轮 subagent 的完整输出——那是过程，不是给用户看的交付物。
