# Grilling：把需求问透再动手

`design-execute-audit` 的 Step 0 和 Step 1 都从「任务已经明确」开始，`user-preferences` 的「目标与路径」说了目标不清楚要停下来讨论——这个 skill 是那个"停下来之后"的具体问法。产出不是代码，是一份双方都认的共识。

## 开场：先承认自己在猜

问第一个问题之前，先写一句当前理解和一个置信度：

```
我的理解：你要的是 <一句话>
置信度：~30%——缺：给谁用、什么算成功
```

置信度低于 70 就把缺的东西列出来。这个数字的作用是逼你承认哪里在猜：如果你写了个高分，却预测不出用户对接下来三个问题会怎么答，那这个数字就是错的。

## 设计树与前沿

把待定的东西看成一棵**设计树**：每个决策都会岔出挂在它下面的决策。

**前沿**是所有前置已经定了、现在就能问而不用猜答案的问题。一轮问完整个前沿，用户的回答会重塑这棵树：定下来的决策把前沿往外推，解锁原本依赖它的问题。重算前沿，问下一轮。

**答案依赖本轮另一个未决问题的，属于下一轮，不要塞进这轮。** 这是唯一一条硬规则——违反它就是在拿自己的假设当前提提问，用户答完你还得重问一遍。

## 每轮怎么问

一轮批量问，每题带你的推荐答案：

```
❓ **Q1 - <问题标题>**：<问题正文，可以给选项>

➡️ <你的推荐答案>

---

❓ **Q2 - <问题标题>**：<问题正文>

➡️ <你的推荐答案>
```

- **批量，不是一次一题，用问题卡问。** Claude Code 里 AskUserQuestion 一次能问 4 题带选项，正好装一轮前沿；Cursor 用它的问卷卡（AskQuestion）。一次一题会让用户为一个需求答十几个来回。例外是手下还有泳道在跑的统筹会话：问题卡会挂住整个会话，泳道消息全部排队，改用回复末尾的文字问题并结束本轮（见 `parallel-coordination`）。
- **每题必须附推荐答案。** 用户反驳一个错的猜测，比从零想一个答案快得多；而且这逼你把自己的假设摆到台面上被打，这正是这个流程要的效果。
- 偶尔往你预期会被推翻的方向猜。客气的用户会顺着你的推荐答案点头，那样问了等于没问。

## 事实自己查，决策交给用户

- **需要环境事实**（代码里到底怎么写的、这个库支不支持、现在的配置是什么）→ 自己查，量大时派子代理；用户的时间只花在决策上。
- **查着的时候不阻塞**：正在跑的调查是一个未定的前置，只有依赖它的问题要等，前沿上其余的问题照问。
- **交给用户的决策**是 `user-preferences`「问与不问的分界」里先问的那一类：意图或语义的歧义、砍范围、页面形态与导航、新增产品表面、推翻用户定过的口径。这一类哪怕推荐答案毫无悬念，也摆出来等回答。技术取舍、视觉数值与档位、能从设计稿和参照推出来的口径，按推荐定下，在共识复述里标出来。

## 什么时候结束

前沿为空——每条分支都走到过，没有一个还在靠默默假设撑着。这时复述一遍共识（要做什么、给谁、什么算成功、有哪些硬约束、明确排除了什么），**等用户确认之后**再进 `design-execute-audit` 或直接开工。没确认之前不要写任何代码。
