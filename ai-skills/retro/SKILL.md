# 会话复盘

复盘的对象是 **agent 的运行环境**，不是这次的产出。问的是"下次同样的活怎么能少走这些弯路"，答案落在规则文件、自动检查、工具和信息可达性上。

## 步骤

1. **先调 `writing-for-agents`**——复盘的产出多半是要写进某个 agent 读的文档里，写法标准在那儿。
2. **读一手材料**：用户指定的那次会话（可能要翻本机的 session 日志），没指定就是当前这次。凭印象复盘等于编。
3. **按下面的类别找候选**，每条都要能指到本次会话里的具体位置——找不到具体位置的不是发现，是感想。
4. **按严重程度排序呈现，然后停下**。复盘的候选是你自己找出来的，排好序交给用户取舍。两种例外按 `user-preferences`「沉淀规则与 skill」当回合落盘：用户当场的纠正，以及已经造成过失败的过期或写错的规则。

## 候选类别

| 类别 | 什么时候该找它 | 典型产出 |
| --- | --- | --- |
| 导航 | agent 花了很久才找到该改的文件 | 在常驻文件里加一条导航指针 |
| 自动检查 | 犯的错本可以被 lint / 类型检查 / 测试抓住 | 补一条检查，而不是补一条"要小心"的规则 |
| 审计规则 | 审计没抓住的问题 | 给审计方加一条规则，或把已有的那条讲清楚 |
| 常驻文件体积 | 常驻规则文件大到开始互相稀释 | 把某几节下沉成按需加载的 skill 或自动检查 |
| 工具经济 | 出现了很贵或很啰嗦的工具调用 | 换个查法，或包一个更省的命令 |
| no-op | 常驻文件很大但不见效 | 找出那些相对模型默认行为没改变任何东西的句子，整句删 |
| 信息可达性 | 有关键信息 agent 根本拿不到 | 把日志接出来、给只读访问权限 |

## 一条值得记住的分工

所有工作都会经过实现和审计两段，两段的**上下文压力**完全不同：实现方要探索、写代码、调试，上下文最紧张；审计方拿到的是 diff，不需要探索，通常也不写代码。

所以**编码标准应该由审计方执行，不是压给实现方**。往实现方的常驻规则里堆标准，是在最缺注意力的环节加负担；同样的标准挂在审计侧，命中率高得多。复盘时看到"某条标准反复没被遵守"，先问它是不是挂错了环节。
