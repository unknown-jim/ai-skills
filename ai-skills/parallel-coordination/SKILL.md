# 并行统筹

一个会话拿着**集成分支**和**共享文档**，N 个 chip 各在独立 worktree 交付，统筹合并、验证、裁决。
统筹存在的意义只有一条：**把各泳道的问题攒起来一次问用户。** 它防的失败是**无法归并的决策分叉**——
两条线各自弹窗问了用户、拿到相反的答复、而谁先谁后只有用户自己知道（2026-09-04 实发）。

下面每条规则后面括号里是它防的那次具体失败。规则读不懂时读括号。

## 0. 开工前钉三件事

1. **集成分支**归统筹自己的 worktree 维护；不开 MR，直到用户要（总集分支出特性包给测试，全做完才 MR）。
2. **共享文档里的待决清单**在哪、**号段怎么分**（例：G240–G244 归 A、G245–G249 归 B）。两条线各写一个 G10 是真发生过的。
3. **统筹会话的真实标题**。下游靠标题找你；派活模板里写一个自己编的标题，下游按它找会找不到（2026-09-04 实发）。

## 1. 切工作：切在哪、切多粗

- 一个稿上位置常同时属于两个特性（修饰键行第 1 格既是「修饰键顺序」又是「组合键开关」），
  按屏切必然派重；**按 token / ARB key / 文件切**，冲突才发生在切分线上而不是切分线里。
- **一个事实一个负责人**：同一档字号落在三个类里，也只派给一个人；删一个符号只派一个人，
  哪怕它跨四个文件（两个人删同一个符号、各解一半冲突，2026-09-04 差一点发生）。
- **每份 prompt 里互相声明文件所有权**：「A 拥有 X / B 拥有 Y / 你拥有 Z」。
- 下游用**独立 worktree**，不用统筹自己的（统筹在同一棵树上合别的线，两个会话抢一个 checkout，2026-09-03 实发）。

**切多粗，按项目定，但用同一组判据**（用户原话：「可以开多个 chip 并行，但不要切得太碎」）：

- **一个 chip = 一块能独立验证的东西**：它有自己能跑的测试子集、能出自己的 golden、能单独说清「做完了」。
  一条常量改动、一处文案，不够成一个 chip；「数值 / 文案 / 键位表」三类共 25 处才是。
- **切分线落在文件所有权边界上**：两个 chip 要改同一个文件，就先合成一个，或把那个文件明确划给其中一个。
- **并行数受统筹吞吐限制**：每个用户 turn 只能发 10 条跨会话消息，每个 chip 至少要一轮派活、一轮拍板、一轮合并回执。
  三到四条并行是这两条线实测能服务过来的上限；再多，统筹先被限流卡住，chip 排队等裁决。
- 每多一个 chip 都要付一遍固定成本：建 worktree、读文档、跑基线、rebase、合并、解冲突。切碎的代价是这些成本乘以 chip 数，
  而不是并行省下的时间。
- **实现之前先派一轮只出清单的**（差异清单 / 缺口清单），拿清单和量级再决定切几刀——
  这轮 A 组「约 25 处、一轮偏大、可以拆成两半」的判断就是清单那轮给的，比凭感觉切准。

## 2. 派活 prompt：五段，密度按 engineering-discipline

范围 / 所有权 / 验证判据 / 已知坑 / **决策路径**。前四段的写法见 engineering-discipline
「Audit-to-Implementation Prompt Design」，这里只写统筹特有的第五段和几条常见漏项。

**决策路径必须写全**，缺一条就会出现绕过统筹的分叉：

- 统筹的**真实标题** + 找法：`list_sessions` 按标题取 sessionId，`send_message` 发。
  `ListAgents` 只给自动代号、且不列 idle 会话，靠它找不到。
- **找不到统筹时**：把决策点写进共享文档的待决清单（用分给它的号段，表行与小节两边都写），
  **按自己的判断继续**，不停下等。这是用户 2026-09-04 明确裁定的口径——「你决策不了的直接绕过」。
  另一条线曾写成「标待统筹决策并停在那儿」；两种写法里用户明确选了绕过，以后统一用它。
- **AskUserQuestion 弹出去的窗永远落到 user，落不到统筹。** 派活里写「来问我」，下游在自己的对话框里
  看到的「我」是键盘前的用户，这句话就讲不通——所以要把上面两条写成动作，不写成「问我」。

常见漏项：

- **读数会过期**。写进 prompt 的分辨率、屏数、设备状态是几小时前量的；加一句
  「自己重读，别抄本 prompt 里的数」，这句救过一次（被控端从三屏读成单屏）。
- **给出的基线 SHA 要在远端存在、并且自己跑过测试**。revert 完忘了 push、拿本地 SHA 指导三条线 rebase，
  本地对象库共享所以各线 rebase 都「成功」，真合时才发现基线远端没有；rebase 出来的基线只跑了 analyze
  没跑测试，3 条失败被下游归因成「存量」——两件都是 2026-09-03/04 实发。
- **失败数只取跑完那次的**。从进度行读到 `-39` 就写进派活单，那次全量还没跑完。
- 转给下游的**上游结论**要求它按同样规格复验，不是照单全收（下游复验挡住过一次错误结论）。

## 3. 收消息与裁决

- 下游把决策点编号（D1 / D2 …），统筹**逐条拍板**，每条给结论 + 一句理由。
  口径统一是「**不阻塞实现**」：稿面矛盾按更审慎的一侧落地，外部依赖挡住而不是假装满足。
- **裁决写进共享文档，消息只是通知。** 跨会话消息会限流、会交错、会被下游转述后失真；
  文档是唯一一份大家都会回去读的东西。同一条裁决在两轮消息里说了两遍还没送到，文档一次就到。
- **下游顶回统筹的指令是正常路径，不是抗命。** 统筹让重出 22 张 golden，下游只重出真正失配的 1 张
  并说明为什么（校验比覆盖强）；统筹让 push，下游拒绝（对外动作要用户批准）。两次都是下游对。
- **统筹裁错要当场认、并改文档**。「G253 我裁错了，你是对的」比坚持自己的判断便宜得多；
  错误裁决留在文档里会被下一个人当定论。
- **转述的计数不是数过的。** 统筹说「7 处」，下游自己数是 11 处；统筹说「22 张要重出」，实际失配 1 张。
  自己没数过的数字，写出去时标「未核」，或者让下游自己数。

**统筹的权限边界**：能拍技术口径、能合并自己维护的集成分支、能定合并顺序；
**不能批准 push / 开 MR / 装机 / 发消息给外部**——这些只在用户明确要求时做。
「我是统筹」不是授权链的一环，下游据此拒绝是对的。

## 4. 合并循环

每收到一条完成消息：

1. **核实改动真落地了**（`git diff --stat`，不是读它的完成声明）。
2. **合并顺序**：先合改共享 token / 删符号的那条，后合新增的；后合的那条 rebase 时冲突「一律取删」。
3. 每合一次：**gen-l10n（带新 ARB 时）→ analyze → 相关子集测试**。只跑 analyze 不算验过。
   合完带新 ARB key 的分支不先 gen-l10n，会得到一堆「getter 未定义」，酷似下游没做完。
4. **基线漂了就让作者 rebase，不替它解冲突。** 14 个冲突里有 4 张二进制 golden 和三份 ARB，
   统筹分不清 token 文件里哪段是谁的意图。作者 rebase 时提醒两条：批量「两边都保留」会把邻居的类
   从中间截断、而报错指向自己新加的类（2026-09-04 实发）；**同名不同类按类定位**
   （`awk '/^abstract final class X/,/^}/'` 先切出作用域再看里面），一个文件里 `titleStyle` 裸 grep 有 7 处。
5. **判交集用对基准**：平行分支之间用 `git diff <base> origin/<branch>`；**从集成分支长出来的分支**
   不能用这个写法，会把别人的文件算到它头上，然后拿一份错误的冲突清单去找它。
6. **全量跑着的时候，合并排在它跑完之后。** 中途合进去的代码，后加载的测试会用到，那一轮的数字是混的、只能重跑。
7. **golden**：先跑校验（不带 `--update-goldens`），**红的才进重出流程**，绿的不碰。
   校验 = 图与当前渲染相等；重出 = 把当前渲染写进图不论对错。「累计 diff 张数」和
   「相对当前代码的失配张数」是两件事，`git diff --stat` 给的永远是前者（22 vs 1）。
   二进制冲突取任一侧都是过时的图，要在**合并结果**上重出。

## 5. 收口

- **一次干净的全量**，判据是失败集合与基线**逐文件相同**，不是失败数相同。
- 给用户一份：裁决清单 / 仍需外部输入的问题（按谁来答分组）/ 本期明确不做的。
- **当天的教训要 `send_message` 给还在跑的兄弟会话。** 常驻记忆索引是会话启动时的快照，
  只写记忆等于只对明天启动的会话生效；同一天四条线出过三次同形错误，解药写下来时它们已经犯完了。

## 跨会话通信的硬约束

- **找统筹**：`mcp__ccd_session_mgmt__list_sessions`（有 title / cwd / isRunning）→
  `mcp__ccd_session_mgmt__send_message`（idle 会话也收得到，排队到它下次活动）。
- **限流**：一个用户 turn 里最多发 **10 条**跨会话消息，超了全部拒绝，直到用户在这个会话里说话。
  中间收到的 chip 消息和系统通知**不算**用户说话。所以：攒着批量回、裁决落文档；同一条内容送达过一次就够，
  交错了也用文档兜底而不是再发。
- **「已通知 X」必须对应一次真实的 send 调用。** 在给用户的回复里用「问对方」的口气写一段，
  对方什么都收不到，而回复读起来完全像已经发了。

## 共用真机

多条线共用一台设备时**装机由统筹统一做**，下游交付到「构建成功」为止。谁都自己装会互相盖包，
iOS 侧没有 Android 那种包体字节数校验，被盖了看不出来。租约工具的用法见项目私有规则。

## 什么时候不用这套

单条变更流（一个人从调查到交付）用 engineering-discipline；线性的设计 → 执行 → 审计用
design-execute-audit；换会话接着干用 handoff。这套只在**同时有多条泳道往一个集成分支交付**时值回它的开销。
