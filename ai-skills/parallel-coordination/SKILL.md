# 并行统筹

一个会话拿着**集成分支**和**共享文档**，N 个 chip 各在独立 worktree 交付，统筹负责合并、验证、裁决。
统筹存在的意义：**让每个决策只在一处拍板**——技术口径统筹自己拍，`user-preferences`「问与不问的分界」里先问的那一类
攒起来一次问用户。它防的失败是**无法归并的决策分叉**——两条线各自弹窗问了用户、拿到相反的答复，而谁先谁后只有用户
自己知道（2026-09-04 实发）。

下面每条规则后面括号里是它防的那次具体失败，规则读不懂时读括号；`references/` 下的四个文件只在用到的那一步指过去。

## 0. 开工前钉五件事

1. **集成分支**归统筹自己的 worktree 维护；用户没要之前不开 MR（总集分支出特性包给测试，全做完才 MR）。集成分支和 chip
   分支第一次推要用户原话授权（见第 3 节末「统筹的权限边界」）；没有授权的 chip 交付到本地 commit，统筹从共享对象库合。
2. **共享文档**放仓库外的固定目录（例 `~/Work/<project>-handoffs/<主题>-<日期>/`），一次统筹一个目录，COORD.md、
   PROMPT-<泳道>.md、证据都放里面，不放进主 checkout，也不随集成分支进仓库；泳道按号段直接写自己的行，统筹写裁决。
   先立三张表：「用户已定口径」（编号、日期、原话，照做不问）；**号段**（例：G240–G244 归 A、G245–G249 归 B；统筹自己也从表里
   取号、自留一段，每次派活和再派第一句写号段，只凭明确回报收回）；**在飞账本**（号段 → chip 的 sessionId / 分支 / 状态，外加
   每条裁决发给过谁），派活、再派前先查，重派前先看旧的那条起没起（两条「泳道 3」并行跑过，2026-09-15）。它是长寿文档，按
   `engineering-discipline`「Long-Lived Plan Documents」管（行数预算、按当前状态重写）；骨架见 `references/dispatch-template.md` 末节
   （两条线各写一个 G10、755 行的文档里叠了六层「以本节为准」，都是真发生过的）。
3. **统筹自己的 sessionId**：`get_session self` 取到原样抄进共享文档和每份派活，标题只作交叉核对
   （凭印象编的标题被抄进至少 7 份派活，2026-09-07；标题还会中途改名）。
4. **贵的一次性中间产物统筹产一次**：基线失败名单（各泳道受影响子集的并集上跑一次，命令、读数、退出码进文档）、
   解码好的日志、基线树，放共享目录，泳道据此归因、不各自重跑。
5. 有兄弟统筹或相邻领域的会话在跑时，先对一次共享面和行为依赖（`references/cross-session.md`「本统筹之外的会话」）。

## 1. 切工作：切在哪、切多粗

- 一个稿上位置常同时属于两个特性（修饰键行第 1 格既是「修饰键顺序」又是「组合键开关」），
  按屏切必然派重；**按 token / ARB key / 符号 / 文件切**，冲突才发生在切分线上而不是切分线里。
- **一个事实一个负责人**：同一档字号落在三个类里，也只派给一个人；删一个符号只派一个人，
  哪怕它跨四个文件（两个人删同一个符号、各解一半冲突，2026-09-04 差一点发生）。
- **每份 prompt 里互相声明所有权**：「A 拥有 X / B 拥有 Y / 你拥有 Z」，列到编译单元和必经入口（part 文件随主文件，
  facade / 转发层点名），生产、测试、生成文件都列；清单外的无主文件由下游开工时列出、统筹追认。公共路径、共享文件
  （设计文档、CI 配置、`.gitignore`）、计数与预算类门禁常量默认归统筹：泳道不改，记待决按默认继续。
- 两条线要动同一个文件：合成一个、把文件划给其中一个，或者**按符号划飞地**（非负责方先登记挂接点，统筹批准后
  通知负责方避开）。**接口先行**：多条泳道要用的共享件先由拥有者单独提一个最小 commit、合入并广播，再开依赖它的泳道；
  接线的时机和执行人写进裁决（没写接线人，引出过一个 BLOCKER）。跨泳道交互点的联调用例归谁写，切完就定。
  这几种的做法见 `references/dispatch-template.md`「所有权」段。
- 下游用**独立 worktree**，不用统筹自己的（统筹在同一棵树上合别的线，两个会话抢一个 checkout，2026-09-03 实发）。

**切多粗，按项目定，但用同一组判据**（用户原话：「可以开多个 chip 并行，但不要切得太碎」）：

- **一个 chip = 一块能独立验证的东西**：它有自己能跑的测试子集、能出自己的 golden、能单独说清「做完了」。
  一条常量改动、一处文案，不够成一个 chip；「数值 / 文案 / 键位表」三类共 25 处才是。
- **并行数受统筹的服务能力限制**：每个 chip 至少要一轮派活、一轮拍板、一轮合并回执，统筹还要逐条核实改动真落地、
  按顺序合并、每合一次跑一轮验证。三到四条是实测能服务过来的上限；再多，裁决和合并开始排队，chip 空等统筹。
  每多一个 chip 都要付一遍固定成本（建 worktree、读文档、跑基线、rebase、合并、解冲突），切碎的代价是它乘以 chip 数。
- **不够成一个 chip、又不带语义判断的改动，统筹在自己的树上做掉**：一行诊断日志、一处常量、一次 revert、一条注释订正
  （2026-09-06：为一行 `traceId` 探针提议开 chip，用户当场问「一行也派单独 chip？」）。判据看有没有语义判断、不看行数：
  接线、改共享 API 哪怕一行也派回拥有者泳道或单独过审计（亲手接的线漏了出口，2026-09-15）；统筹的提交跑同一套门禁、
  收口时单独指给审计。要守的是**集成分支不被并发写坏**，不是「统筹不碰代码」——写在自己维护的诊断 / 集成 worktree 里，
  不占别人的树。
- **实现之前先派一轮只出清单的**（差异清单 / 缺口清单 / 同形实例盘点），拿清单和量级再决定切几刀，
  派「实现某功能」之前先查远端有没有现成的未合并实现。这轮 A 组「约 25 处、一轮偏大、可以拆成两半」的判断就是清单那轮给的。
  按设计稿改版、做组件或接口迁移的，清单怎么取、画板覆盖表见 `references/ui-lanes.md`。

## 1.5 定档：哪些 chip 内部要跑 DEA

切完工作、写 prompt 之前，**每个 chip 过一遍这张表**，结果写进派活 prompt。不逐个定只有两种结局：复杂的那条裸奔，
或者凭感觉全都加上——N 条各跑一轮 `design-execute-audit` 是 N × 3~5 次强模型调用，把并行省下的时间用订阅额度和时长买回来。

| chip 的形态 | 派活时定的档 |
|---|---|
| 根因未定的 bug（症状清楚、为什么这样不清楚） | 内部跑 DEA，**开 Step 0 根因锁定** |
| 会引入或改动一层抽象、跨模块边界、影响以后怎么扩展 | 内部跑 DEA，**开 Step 1.5 方案红队** |
| 门禁、校验器这类「挡东西」的改动 | 内部跑 DEA，第一轮就配对抗红队（专找绕过）和合成阳性自测 |
| 方案具体，但还有一两处要实现判断（派活里留了「你定」的也算） | 不跑完整 DEA，实现完成后起一次独立审计 |
| 方案已经具体到照着做就对的批量改动（数值 / 文案 / 键位表这类） | 不跑，按第 2 节直接派 |

**判断放在切完之后，范围中途扩大时重新定**：25 处数值拆成两个 chip，两个都是机械档；
把「删符号」和「改所有调用点」并成一个 chip，它就跨了模块边界。

- **内部跑 DEA 的 chip 自己起审计子代理，审计结论不上交统筹**；worktree 不用另开，DEA 整条链复用它自己那棵树。
- **进内部循环之前先报一声**（「进 DEA 内部循环，预计 N 轮」）。循环在跑的那段时间，统筹的消息可能一直进不来：
  急事统筹自己处理，或等它报下一步。chip 进 Step 1.5 红队时，统筹把它那棵树里看不到的跨泳道风险和仓库禁令列成必查项；
  DEA 中途的回报，只有影响正确性或跨泳道口径时才打断追问。
- **内部审计 FAIL 的归因决定它归谁**：`执行偏离方案` 和纯泳道内的 `方案本身有缺陷` 走 DEA 自己的循环，不上报；
  缺陷涉及**跨泳道口径**（共享 token、要删的符号、ARB key 怎么命名）时，按第 3 节编号送统筹裁决——泳道内自己改对了、
  跟隔壁不一致，要到合并才发现。
- **chip 撞上 DEA 的停下出口就停下报统筹**（停点、Step 0 补过观测仍锁不定根因、读数要真机或用户账号，见派活模板第 4 项），
  找不到统筹就停着等，不自己放宽标准：属于 `user-preferences`「问与不问的分界」先问那类的，统筹问用户；
  同类失败第二次出现的，chip 附上结构性方案的建议，统筹定缩范围还是换切法，越出先问那一类的再问用户。审计通过后追加的提交按 DEA「循环规则」复核、回报单列。
- **在跑的审计或 DEA 循环不去动它的树**：统筹的 rebase、基线变更写「等当前审计出结论再做」；有待裁决项会改代码的，
  先把待决发出去、裁决回来再起审计（一轮审计 FAIL 的 3 条正好是已经裁过的）。新增范围开新变更流排在它后面；
  没在循环里的在跑 chip，范围变了就发增量，不另派一条。

## 2. 派活 prompt

凡是会让下游动手的消息——首派、再派、收口打回、CI 红叫回、启动后扩范围、中途追加一类新操作——都照
`references/dispatch-template.md` 的骨架写，逐 chip 只填差异，密度按 `engineering-discipline`「Audit-to-Implementation Prompt Design」。
授权和回报对象逐 chip 写；订正口径时改模板源，再给已派出的 chip 逐个补发（「不走统筹、可以自己推」被固化进模板，连发 4 条，2026-09-08）。

**决策路径必须写全**，缺一条就会出现绕过统筹的分叉：

- 统筹的 sessionId 原样加当前标题；回报通道按 chip 形态写：独立会话发消息给这个 id，子代理的最终输出就是回报。
  `ListAgents` 里的自动代号不抄进派活（09-08 按代号投递，not found 6 次）。
- **找不到统筹、或者统筹还没回时**：把决策点写进共享文档待决表里自己号段的那一行，
  先 commit 与它无关的那一层，**按自己的判断继续**，不停下等。这是用户 2026-09-04 明确裁定的口径——
  「你决策不了的直接绕过」；另一条线曾写成「标待统筹决策并停在那儿」，用户明确选了绕过。例外是 chip 内部 DEA 的停下出口
  （派活模板第 4 项）：那几种停下报统筹、等统筹回话。
- 决策请求写成：编号、推荐、证据等级、对推荐不利的读数、选它的代价（列最重那一格）、默认值和何时按默认生效
  （漏了最重那一格的代价陈述，让裁决当场翻过一次，2026-09-08）。
- **AskUserQuestion 弹出去的窗永远落到 user，落不到统筹。** 派活里写「来问我」，下游在自己的对话框里看到的「我」
  是键盘前的用户——所以把上面几条写成动作，不写成「问我」；稿里读不到的细节写成「你自己定，回报里标出来」——写成「先交用户确认」，
  chip 会去问它自己会话的用户，统筹拦不住（一条 chip 因此停了约 4 小时，2026-09-26）。

常见漏项：

- **完成回报要和决策路径分开写，并写成动作**：「完成后给我发一条会话消息」，字段照模板。只写「把 SHA 报回来」，下游会在
  自己的终端里作答就收工；并进决策路径写，下游会把「**有分叉**来问我」当成回报的总开关，没有分叉就连完成回报一起免掉
  （2026-09-06 实发，用户问「为什么不同步给统筹」才补发）。
- **事实断言带出处**：写下的每个事实——数字、调用链、「只有一处 / 不存在」、改动在哪条 ref 上、稿上有什么——后面带
  〔出处：命令 / 节点 / 符号 / 读取时刻〕，没亲手读过原文的标〔未核〕；零命中附正对照，先例附成立条件
  （写法见 `references/dispatch-template.md`「前提」段）。再预先写一句：前提与实测冲突以实测为准，下游备案后继续
  （12 个统筹会话里 57 起前提错误，全靠下游复验挡下，每起多一到三轮往返）。
- **读数会过期**。写进 prompt 的分辨率、屏数、设备状态是几小时前量的；加一句「自己重读，别抄本 prompt 里的数」，
  这句救过一次（被控端从三屏读成单屏）。转给下游的**上游结论**也要求它按同样规格复验（下游复验挡住过一次错误结论）。
- **基线给规则不给值**：「以你 rebase 那一刻 fetch 到的 tip 为准，回报写实际值」；要钉死时（revert 之后、栈式依赖）才给 SHA，
  给之前确认下游真能取到它、自己跑过测试；统筹要往集成分支提交的先提交完再派活。（revert 完忘了 push、拿本地 SHA 指导
  三条线 rebase；rebase 出来的基线只跑了 analyze，3 条失败被下游归因成「存量」——都是 2026-09-03/04 实发。）
- **失败数只取跑完那次的**。从进度行读到 `-39` 就写进派活单，那次全量还没跑完。
- **验证判据先写「什么读数能证明用户看到的东西变了」**，再往回推：点名的变异点和负断言是意图不是实现，要下游在当前代码里
  落位、证明在用例路径上；断言配负对照（「被测逻辑整个不存在时会不会照样绿」）。同一个 bug 改多个入口的，范围写成
  「所有到达 X 的调用点（按汇点 grep）」，第一条回执先交清单。画 UI 的泳道把还原判据照 `references/ui-lanes.md` 写进去
  （2026-09-29：派完才被提醒细节和暗色）。

## 3. 收消息与裁决

- 下游把决策点编号（D1 / D2 …），统筹**逐条拍板**，每条写「结论（意图 / 要满足的属性）＋判据＋一句理由」：
  点名的 API 和写法标「建议，需实测」；改变共享语义的，写出断什么、反例、改哪处必须变红；要等实验的写成条件裁决；
  按推荐落地或有意偏离稿面的单开一行，写成立前提和重议条件；**改了范围或所有权的**（含统筹自己要动、划飞地、收工、接管），
  同一句写清哪个文件、动哪几行、原拥有者哪些测试必须保持绿，同时发给双方。下游照结论执行、逐条验理由，理由不成立当场回报
  （一条裁决点名的 `addTearDown` 实测用不了，2026-09-17）。口径统一是「**不阻塞实现**」：稿面矛盾按更审慎的一侧落地，
  外部依赖挡住而不是假装满足；「不动」不是中立选项，「审慎」也不等于保持现状。
- **哪些自己拍、哪些问用户**，按 `user-preferences`「问与不问的分界」：直接拍的在交付里列出；先问的那一类第一次回报就逐项
  摆给用户（2026-09-27：照搬 09-10 的例外名单定了一个页面的展示形态，从没单独说过，收口后撤出例外返工）。
  需求原文点名了上交路径的，每一项例外都走那条路。
- **问用户不用问题卡**：手下有泳道在跑时，先把待合、待回的处理完，问题写在回复末尾并结束本轮，长验证放后台。
  问题卡和长时间的前台命令都会挂住整个会话，挂着的这段时间所有泳道的消息都只能排队（一次挂了 7 小时 12 分）。
- **拍板之前先自检**：追加要求、改判、或说「你自己定」之前，先读泳道当前的方案和用例清单；数据回一手来源（稿的节点、
  源码、原始日志）去读；拍「同意 / 一律按默认」前 grep 改动符号的全部调用方、把改前行为列成表；能查清的事实先查掉；
  改判前拿自己一直用的判据套一遍新证据；裁「保持基线不变」前确认基线本身不是 bug。同一条泳道 10 分钟内被改判两次以上，
  先发「停在当前提交，等定稿」（一个常量裁了甲、乙、钉死、再订正，80 分钟 22 条消息，2026-09-08）。
- **裁决写进共享文档，消息只是通知。** 跨会话消息会交错、会被转述后失真，文档是唯一一份大家都会回去读的东西。
  **一条裁决只有一个家**：待决表那一行是索引和当前状态（结论＋一句理由＋落地 SHA），小节只放论证、挂编号，改判就在那一行上改；
  合并记录和派活 prompt 只引编号不抄值；跨泳道的接线须知把原文落进文档。写法细则见 `references/dispatch-template.md` 末节
  （同一事实在两节和派活 prompt 里各写一份，作废一处没人改；只转了签名没拍板的一条一直是「待」，被收口审计判漏裁）。
- **跨泳道的语义依赖在裁决时登记**：「X 泳道在改 Y 的语义，你的判据依赖 Y 的哪一面」，要求写注释、加守卫用例；跨泳道用例只断
  本泳道负责的量，过渡期的宽断言（anyOf）写明谁在哪一步收紧（三条泳道各自 AUDIT PASS、合起来才坏；一道定序门在兄弟泳道
  合入后失去全部覆盖，摘掉它全量照样绿）。
- **下游顶回统筹的指令是正常路径，不是抗命。** 统筹让重出 22 张 golden，下游只重出真正失配的 1 张并说明为什么
  （校验比覆盖强）；统筹让 push，下游拒绝（对外动作要用户批准）。两次都是下游对。
- **统筹裁错要当场认，并改到每一处使用现场**。「G253 我裁错了，你是对的」比坚持自己的判断便宜得多；错误裁决留在文档里
  会被下一个人当定论。订正——含撤销、修订、收回自己的论证——先列现场：共享文档那一行、派活模板源、发给过哪几条 chip
  （查在飞账本）、MR 描述、记忆正文和索引行，逐处改完再 grep 一遍被订正掉的那个词；结论不变而论证被证伪也照此办。
- **转述是线索，不是事实。** 跨泳道转达写成「线索；我验到：…」；下游报上来的全称否定、机制推断，写进裁决或注释前统筹按
  汇点或上游源码自己验，验不了标 INFERRED、先只定归属。复核要换入口，沿对方给的链再读一遍不算。**转述的计数不是数过的**：
  统筹说「7 处」，下游自己数是 11 处；自己没数过的写出去标「未核」，数对不上先比口径。
- **别的泳道地盘里的缺陷**：发现方带证据等级上报、那条用例保持红；统筹编进所有者号段，要求「先复现：属实就修，不属实给证据」，
  告诉发现方「你不用动」，再按「谁抄了同一种写法」扫兄弟泳道；两条以上泳道撞上同一缺口，到共享件的根上修。泳道交付里的残留
  按来源分流：本泳道引入的交付前修掉，既有缺陷在本模块内就修、收口单列，越出模块另开任务（`engineering-discipline`「Audit Calibration」）。
- **会影响别的泳道的教训、工具坑、环境变化，当轮 send 给所有在飞的 chip 和还在跑的兄弟会话，并改共享文档。** 常驻记忆索引是会话启动时的快照，
  只写记忆等于只对明天启动的会话生效；同一天四条线出过三次同形错误，解药写下来时它们已经犯完了。

**统筹的权限边界**：能拍技术口径、能合并自己维护的集成分支、能定合并顺序。push、开 MR、合并 MR、删远端分支，以及授权怎么认定，
按 `user-preferences`「对外动作」；装机和给外部的人发消息只在用户明确要求时做（「构建到 X 测试」就是要求）。下游拒绝统筹
转述来的授权是对的。「我是统筹」不是授权链的一环，也不让别的会话去做本会话被拦下的动作（SendMessage 官方说明称之为
permission laundering）。项目规则写明要用户授权的事项（例：超限文件变长或拆分），统筹不批：按项目默认做（不变长、新增职责
拆出），要越过规则的那一处列进先问清单，第一次回报就摆给用户。叫停或作废 chip 按 `references/cross-session.md`
「叫停与作废」：声明作废的 SHA，统筹按 SHA 合，删远端分支同样要用户点头（chip 自删了远端分支、统筹事后追认过，2026-09-08）。

## 4. 合并循环

每收到一条完成消息：

0. **合之前**：集成树的 `git status` 有无主改动先查归属，不基于它、不丢弃；只合完成消息里报来、标了「可以合」的 SHA，
   核对它就是该分支当前的 tip，对不上就回头问（按快照合了早一版、cwd 漂到主 checkout 误合，都实发过）。核对与回执的写法见
   `references/merge-and-rebase.md`「合并前」。
1. **核实改动真落地了**（`git diff --stat`，不是读它的完成声明），并认清它实现的是哪一版裁决：对照待决表，把每条裁决要求的
   验收项在 diff 里找到。改了既有测试、点名了零信号点的，按 `references/merge-and-rebase.md` 审；稿差按 `references/ui-lanes.md` 分流。
2. **合并顺序**：先合改共享 token / 删符号的那条，后合新增的；后合的那条 rebase 时冲突「一律取删」。
   接口和共享件的最小提交单独合、单独广播；双方都是加法的冲突两边都留，「以我为准」是优先级，不是删除授权。
3. 每合一次：**先跑项目规则里登记的全部生成器（i18n、聚合 suite 等）→ analyze → 相关子集测试**。只跑 analyze 不算验过；
   带新 ARB key 的分支不先跑 gen-l10n，会得到一堆「getter 未定义」，酷似下游没做完。子集按汇点或文件系统枚举，
   读源码文本的守卫测试固定加进去；「零新增失败」只认全量上按测试名比；红归因成存量、环境或偶发都要附基线读数
   （`references/merge-and-rebase.md`「失败归因」）。
4. **基线漂了先 `git merge-tree` 试合**：零交集直接 `--no-ff` 合并并核对结果，三方计数证明两边都只是追加的统筹自己解；
   其余**让作者 rebase，不替它解冲突**——14 个冲突里有 4 张二进制 golden 和三份 ARB，统筹分不清 token 文件里哪段是谁的意图。
   已经推到远端的 chip 分支，rebase 后推回去就是 force push，按「对外动作」先问用户；没推过的本地分支不受这条限制。
   rebase 的目标与时机、作者要注意的两条、判交集用哪个基准，见 `references/merge-and-rebase.md`「rebase 与判交集」。
5. **全量跑着的时候，合并排在它跑完之后**，也不改写正在跑全量的那个提交：中途合进去的代码，后加载的测试会用到，
   那一轮的数字是混的、只能重跑。
6. **生成物与 golden**：冲突一律在合并结果上重跑生成器或按实数重算，不取任一侧。golden 先校验（不带 `--update-goldens`），
   基线也红的是存量不重出；「累计 diff 张数」不是「失配张数」（22 vs 1）。细则见 `references/merge-and-rebase.md`「生成物与 golden」。
7. 每条回执声明泳道「待命」还是「收工」；收工时它的文件所有权当场转给在岗的泳道或统筹。
8. **同步 master**：并行期间集成分支和泳道都不跟 master，只报交集；开 MR 前统筹 merge（不 rebase）最新 master 一次并跑门禁；
   MR 开出后，每次往它推之前再 merge 一次最新 master、跑门禁（`engineering-discipline`「Finishing a Change Stream」）。集成分支推出去以后按共享分支对待（`references/merge-and-rebase.md`「同步与共享分支」）。

## 5. 收口

- **合完之后先扫一遍待决表里的「待 / 待统筹」**（非空就是漏裁），**再对集成分支做一次审计**（`design-execute-audit` 的 Step 3
  形态，**一次**，不是每条泳道一次）。它防的是各泳道各自 `AUDIT PASS`、合起来仍然坏——泳道内的审计只看得见自己那份 diff，
  第 4 节的机械校验接不住「两条线各自都对、语义上互相矛盾」。给它集成分支的绝对路径、baseline、当前 HEAD 和待决表，统筹自己的
  提交单独列出，不喂各泳道的完成报告；要它对每道跨泳道守卫复验「摘掉它有没有夹具变红」，互为兜底的两道同时摘。跨泳道
  「看起来冗余、其实各有前件」的理由写进代码注释，不写成审计 prompt 里的禁令。语义交互面约等于零时才省掉审计，理由写进文档。
- **收口审计的 P3 默认派给还在的泳道修，不默认「保留」。** 要判「保留」，先逐处读调用点，写出「这几处到底是不是同一个问题」
  的证据，再说它是哪一类（越界的存量 / 结构上修不了）；审计原话写「结构性、保留」不算证据，泳道收口后就没人接了
  （2026-09-26：五处宽窄判定照审计原话判了「结构性保留」，逐处一读是两类问题各一份重复）。
- **收口验证就是项目自己的提交 / MR 门禁**，按 `engineering-discipline`「Finishing a Change Stream」跑；CI 红了按失败文件
  回到对应泳道修。项目没有 MR CI 时才跑一次本地全量，判据是按测试名比，失败集合 ⊆ 基线的失败集合（不新增）
  （2026-09-29：审计已 PASS 还跑了 45 分钟本地全量，项目文档早写了让 CI 代替）。
- 给用户一份收口汇总：裁决清单、能声称 / 不能声称（只说修了哪条路径，写明全量覆盖的是哪个 HEAD）、遗留项按判据分行并写
  收敛条件、顺带修掉的既有缺陷、本期明确不做的（每条附原因）、仍需外部输入的问题（按谁来答分组）、需知会的外部 owner
  （只起草，由用户发）。泳道给的验收口径原样搬进汇总和 MR 描述，不加强。泳道资源按派活里「收尾处置」一段保留到约定事件。

## 跨会话通信的硬约束

- **发给谁**：Claude Code 里用 SendMessage，收件人写对方的 `local_…` sessionId；会话里没有这个工具、或它投不出时，改用
  `mcp__ccd_session_mgmt__send_message(session_id=…)`；回信抄来信的 `from`（官方原文：「To reply to an incoming message, copy its from attribute as your to」）。
  id 只取工具输出或来信：scratchpad 路径的 uuid、task_id、转录文件名、ListAgents 的 [ref] 都不是会话 id（投递失败 11 次，
  多数是拿这几种当了 id）；兜底见 `references/cross-session.md`。
- **读返回值**：delivered = 对方原本空闲，已为这条消息开了新回合。queued 一律当「已发出、未确认」：官方说明写「messages
  enqueue and drain at the receiver's next tool round」，实测却有一个回合从 02:35 跑到 05:24、4 条急件滞留到 05:24（2026-09-24），
  时机不写死。关键指令和裁决同时写进共享文档，对方引用了编号才算送达；急事等不到回执，统筹自己做。
- **每条消息第一行写类型和锚**：类型（决策请求 / 知会·不用回 / 进度·非完成回报 / 完成回报 / 订正 / 叫停，示例见
  `references/cross-session.md`「消息首行」）和它针对的 `<分支>@<SHA>` 或裁决号；收到的消息按锚判新旧、逐条过滤，不按到达
  顺序；改判和叫停写成「对方已经交付」时仍成立的样子（10 个统筹会话里约 35 起交错或对着过期快照下结论，同一件事每次多来回 2–3 条）。
- **「已通知 X」必须对应一次真实的 send 调用**，「已写进 X 号」对应一次真实写入，「我跑过 / 改过 / 没发过」先回查产物；
  会话被压缩后先重读裁决区、号段表和在飞账本再发消息。在给用户的回复里用「问对方」的口气写一段，对方什么都收不到。
- **chip 是子代理时**（Claude Agent、Cursor Task）：最终输出就是回报，它发的消息走父会话的地址、收不到回信；号段和每个待决的
  默认在派活时给全，回稿后统筹把默认逐条转成显式裁决；被中断的子代理留下的改动一律按未验证处理。
- **统筹和 chip 必须同 harness**：Codex 的线程工具见 `references/cross-session.md`；Cursor 没有跨会话消息通道，只能用子代理
  或共享文档。跨 harness 只有共享文档一条通道、没有实时通知，不要混编。

## 共用机器资源

同一台机器上的独占资源由统筹排队：

- **装机**：多条线共用一台设备时，装机由统筹统一做（用户明确要求时），下游交付到「构建成功」为止。谁都自己装会互相盖包，
  iOS 侧没有 Android 那种包体字节数校验，被盖了看不出来。租约工具的用法见项目私有规则。
- **并发跑会把 runner 跑崩的全量测试**只由统筹在合并结果上跑，开跑和跑完各广播一次，期间泳道只写代码、跑 analyze 和汇点子集。
- 停进程只按自己的 PID，改全局 git 配置只用 `-c` 单次覆盖（机器级 `pkill` 误杀过兄弟会话的测试）。
- 动了共享环境（共享 SDK、磁盘、全局缓存）或发现它坏了，广播时间窗和症状；窗口内的失败读数一律作废重取。

## 什么时候不用这套

单条变更流（一个人从调查到交付）用 engineering-discipline；线性的设计 → 执行 → 审计用
design-execute-audit；换会话接着干、或压缩上下文之前，用 handoff。这套只在**同时有多条泳道往一个集成分支交付**时值回它的开销。
