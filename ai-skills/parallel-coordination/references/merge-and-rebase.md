# 合并、rebase 与失败归因

SKILL.md 第 4 节合并循环指到这里，按动作分节：合并前、rebase 与判交集、失败归因、生成物与 golden、同步与共享分支。

## 合并前

- **集成树先干净**：`git status` 有不是自己留下的未提交改动，先查归属（会话 cwd、在飞分支、mtime），不基于它、不丢弃，
  写进文档并报告。合并命令在集成 worktree 里跑，先核对 `git rev-parse --show-toplevel`（cwd 漂到主 checkout 误合过）。
- **核对 SHA**：只合完成消息里报来、标了「可以合」的那个 SHA。合之前在集成 worktree 里用 `git rev-parse` / `git ls-remote
  --heads origin <branch>` 核对它就是该分支当前的 tip；本地交付的，所有 worktree 共用一个对象库，`git cat-file -t <SHA>`
  回 commit 就能直接合，复核也不用等 push。对不上就回头问，不按快照合（按快照合过早一版）。
- **回执**写「合的是你的 <SHA> → 集成 <合入点>（本地 / 已推远端）」，不只写「已合」。
- **已回报的 SHA 只追加不改写**：必须改写时，下一条消息首行写「旧 → 新，树差 = …」；不改写正在跑全量的那个提交。
  统筹自己给出 SHA 之前，跑 `git ls-remote --heads origin <branch>` 和 `git merge-base --is-ancestor` 实核。
- **认方案、找验收项**：读 diff 认出它实现的是哪一版裁决；对照待决表，把这条泳道每条裁决要求的验收项（用例、断言）在
  diff 里逐条找到。
- **改了既有测试**：方向在 diff 里看得见（保留同名用例）、补了正向断言、有变异证明它能变红，三条都满足才放行；被断言的
  元素已经没了，删掉这组断言，不改数值；为绕开别人的缺陷改过的时序，等缺陷修好后恢复；等裁决期间用例保持红，不改期望。
- **零信号点**：下游点名的「合并时可能被静默丢掉的接线」，要它补探测器（用例或断言），不接受「合完我 grep 一眼」。
- **合并后的落地核验分三层**：祖先（SHA 在不在）→ 内容（该改的字串在、不该删的没被删）→ 树（`git rev-parse <提交>^{tree}`
  或逐文件哈希）；判「还差不差东西」比树不比 SHA；统筹自己的提交也过这一套。两边都改过的文件逐段读合并结果，零冲突不算数；
  新出现的红，先查是不是合并造成的语义碰撞（「git 零冲突自动合并，正是最容易蒙混过去的形态」）。

## rebase 与判交集

- **先试合**：派 rebase、定合并顺序、跟 master 之前，`git merge-tree --write-tree <集成 HEAD> <分支 tip>` 试合一次，把冲突
  文件清单写进指令。零交集直接 `--no-ff` 合并并核对；三方计数能证明两边都只是追加的，统筹自己解；其余按文件所有权派回作者，
  在作者自己的 worktree 里解。下游只报漂移和交集，不自己 merge / rebase 到集成分支。
- **目标**：依赖哪条泳道，就 rebase 到它报来的、已过审计的 tip（栈式依赖写明 MR 顺序），不 rebase 到集成分支的 merge commit；
  只有要在合并结果上重出 golden、或要解二进制冲突的最后一条，才 rebase 到集成 HEAD。上游还会追加交付的，等它交齐再给目标。
- **时机**：在飞的泳道只在上游改了它马上要编辑的同一个文件时才中途挪基线，否则做完、push 之前再挪；不为一个非语义提交
  打断正在跑 DEA 的泳道。集成分支前移，只在动到某条 chip 的所有权文件时单独通知它，附文件清单
  （`git diff --name-only <pin> <new>` 和所有权求交集，零交集不动）。
- **提醒作者两条**：批量「两边都保留」会把邻居的类从中间截断，而报错指向自己新加的类（2026-09-04 实发）；**同名不同类按类定位**
  （`awk '/^abstract final class X/,/^}/'` 先切出作用域再看里面），一个文件里 `titleStyle` 裸 grep 有 7 处。
- **双方都是加法的冲突两边都留**：「以我为准」表达的是优先级，不是删除授权。rebase 前留一个备份分支，rebase 后用
  `git patch-id` / `git range-diff` 证明内容没变；备份分支等统筹全量通过之后再删。
- **判交集用对基准**：平行分支之间用 `git diff <base> origin/<branch>`；**从集成分支长出来的分支**不能用这个写法，会把别人的
  文件算到它头上，然后拿一份错误的冲突清单去找它——改从分叉点算（`git diff <集成分支>...origin/<branch>`，三个点）。

## 失败归因

- 每合一次跑的子集按汇点或文件系统枚举，不凭记忆列；读源码文本的守卫测试不会被 import 关系选中，固定加进子集。
- 「零新增失败」只认在全量上按测试名比。基线取集成分支实际合入的那个 master 点（`git merge-base`，不是 prompt 里写的），
  基线失败集合按测试名写进共享文档（统筹产一次，见 SKILL.md §0 第 4 件）。只在已失败的那几个文件里比，不算。
- 把红归因成存量、环境或偶发，都要附基线读数：
  - **存量**：从基线全量里按测试名取；
  - **环境**：在写入那张基线的提交上复跑；
  - **偶发**：同负载下的读数——集成分支原样 / 集成分支回退嫌疑文件 / 基线三组穿插，各跑 20 次以上；「单跑是绿的」不算；
  - 过滤掉注释后改动行数为 0（附过滤前的行数），才沿用上一轮的全量结果。
- 归因腿要和被测树共享生成物状态：在同一棵 worktree 里切 commit，或者在临时 worktree 里先跑项目的生成器再比（被 gitignore 的
  生成物会造成跨 worktree 差异）。二分之前先验两个端点：「好端点」本身是红的，二分出来的结论就是错的。

## 生成物与 golden

- 生成物冲突（聚合 suite、l10n、golden）一律在合并结果上重跑项目登记的全部生成器，不手工合（漏跑一次红了 36 条）。
  「上限计数」类冲突（门禁基线条数、额度常量）按合并后名单的实际条数重算，并双向核对。
- golden 先校验（不带 `--update-goldens`）：校验 = 图与当前渲染相等；重出 = 把当前渲染写进图，不论对错。红的才进重出流程，
  绿的不碰；红的先在基线上复跑，基线也红的是存量，不重出、不提交。
- `git diff --stat` 给的永远是「累计 diff 张数」，不是「相对当前代码的失配张数」（22 vs 1）。二进制冲突取任一侧都是过时的图，
  要在合并结果上重出。
- 同一张 golden 有两个变更原因时，先把基线那部分归因清楚，再在同时包含两个原因的分支上一次重出，commit message 写清归因。

## 同步与共享分支

- 集成分支同步 master 由统筹定节拍，用 merge 不用 rebase（一条长期集成分支上已有 84 个 merge，文档引了 15 个本分支 SHA，
  rebase 会让它们全部失效）；下游只跟集成分支的 SHA。同步之后，逐条复核依赖被改代码的裁决。
- master 前移时泳道不跟，只报有没有交集；开 MR 前统一同步一次，跑项目的 MR 门禁：有 MR CI 的，本地只跑静态与格式检查、
  测试交给 CI；没有 MR CI 的，判据是合并结果的失败集合 ⊆ master 的失败集合。MR 开出后，每次往它推之前再 merge 一次最新 master、
  跑门禁。
- 集成分支一旦推出去（出特性包、开 MR）就按共享分支对待：每次合并或推送前先 `git ls-remote` 比对；远端多出的外来提交按一条
  新泳道过审，与已定口径冲突的报给用户（收口后远端分支被别人推进，那几个提交的实现依据没在收口里审过）。
