# 测试驱动开发

## 铁律

**没有一个先失败的测试，就不写生产代码。**

先写了实现再补测试，那个测试是照着实现写的：它一定通过，也一定不会告诉你实现错在哪。一个从来没红过的测试可能永远绿着，因为它压根没碰到那段逻辑。

## 红 → 绿 → 重构

- **红**——写一个描述期望行为的测试，跑它，看着它失败。**完成判据不是"它失败了"，而是"它以你预期的那个原因失败"**：因为函数名拼错、import 少了、fixture 没建而失败，都不算红，那是测试本身坏了，不是行为缺失。
- **绿**——写让它通过的最少代码。这一步不做设计，不加没被测试要求的东西。
- **重构**——测试是绿的，现在整理代码。每次改完重跑，红了就退回去。

## 修 bug 的形态

1. 写一个按复现步骤触发这个 bug 的测试，跑它，**看它变红**——这一步同时证明了你复现对了、也证明了你理解的症状就是实际症状。
2. 修。
3. 跑，变绿。
4. **验回归测试真的有效**：把修复回退掉，测试必须重新变红；恢复修复，测试变绿。只跑过一次绿的测试，不能证明它盯的是这个 bug。

第 4 步是 `user-preferences`「完成声明」里那一行的完整做法。

## 什么时候不用

诚实地跳过，比硬套一个走形的 TDD 有用：

- **项目没有测试基础设施**。这时"先写测试"实际是"先搭测试框架"，那是另一个任务，规模和风险都不一样——**说出来让用户决定**，不要自己顺手把任务范围撑大，也不要因此就一句测试都不写。
- **一次性脚本、探索性原型、纯配置或文档改动**。
- **用户明确要求先看到能跑的东西**。这时说明代价（这轮的正确性没有测试背书），照做。

## 跟 `design-execute-audit` 的关系

Step 1 的方案里有一项是"怎么验证"。项目有测试套件时，这一项默认就写成**先写哪个测试、它该因为什么而红**，而不是"改完跑一下 npm test"。方案把这件事写清楚，执行环节才有可能真的先红后绿；写成"跑一下测试"，执行方一定是先改完再跑。
